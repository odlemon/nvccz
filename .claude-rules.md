# NVCCZ Project Development Rules

## Project Overview
NVCCZ is an Enterprise Resource Planning (ERP) system for investment fund management with comprehensive accounting, built with Express.js, TypeScript, Prisma ORM, and MySQL.

---

## 1. ARCHITECTURAL PATTERNS

### 1.1 Service Layer Pattern (MANDATORY)
- **Controllers**: Handle HTTP requests, validation, response formatting only
- **Services**: Contain ALL business logic, database operations, and integrations
- **Never** put business logic in controllers
- **Always** delegate to services for data operations

**Example Structure**:
```typescript
// Controller - HTTP handling only
async createExpense(req, res) {
  const data = req.body;
  const result = await ExpenseService.createExpense(data);
  return ResponseHelper.success(res, result);
}

// Service - Business logic
static async createExpense(data) {
  // Validation, business rules, DB operations
  const expense = await prisma.expense.create({...});
  await JournalEntryService.createExpenseJournalEntry(expense);
  return expense;
}
```

### 1.2 Database Transactions
- Use Prisma transactions for multi-step operations
- **Always** wrap related DB operations in transactions
- Ensures atomicity (all succeed or all fail)

```typescript
await prisma.$transaction(async (tx) => {
  const journalEntry = await tx.journalEntry.create({...});
  const expense = await tx.expense.update({...});
  return { journalEntry, expense };
});
```

### 1.3 Response Patterns
- Use `ResponseHelper` for all API responses
- Standard methods: `success()`, `badRequest()`, `notFound()`, `serverError()`
- Never return raw JSON without ResponseHelper

## 2. ACCOUNTING RULES (CRITICAL)

### 2.1 Double-Entry Bookkeeping (IMMUTABLE)
- **EVERY** journal entry MUST balance: `totalDebits === totalCredits`
- Validate balance BEFORE creating journal entry
- Allow 0.01 tolerance for rounding only
- Use `Decimal` type for ALL monetary values - NEVER use `number` or `float`

```typescript
// REQUIRED validation
const totalDebits = lines.reduce((sum, line) => sum + parseFloat(line.debitAmount), 0);
const totalCredits = lines.reduce((sum, line) => sum + parseFloat(line.creditAmount), 0);
if (Math.abs(totalDebits - totalCredits) > 0.01) {
  throw new Error("Debits must equal credits");
}
```

### 2.2 Automated Journal Entry Generation
- **ALWAYS** auto-generate journal entries for:
  - Expenses
  - Customer invoices
  - Purchase invoices
  - Revenue
  - Cashbook transactions
  - Fund disbursements
- Link via `journalEntryId` foreign key
- Never create source document without corresponding journal entry

### 2.3 Reversal Workflow (MANDATORY for Posted Transactions)
- **NEVER** directly update/delete posted transactions
- **ALWAYS** create reversal entry first
- Reversal entry has opposite debits/credits
- Reference number prefix: `VR-` or `REV-`
- For updates: Create reversal + new entry
- For deletes: Create reversal + soft delete

```typescript
// Correct pattern for updating posted expense
async updateExpense(expenseId, newData) {
  const expense = await prisma.expense.findUnique({...});

  if (expense.status === "POSTED") {
    // Create reversal journal entry
    await JournalEntryService.createReversalEntry(expense.journalEntryId);
    // Create new journal entry with new amounts
    const newJournalEntry = await JournalEntryService.createExpenseJournalEntry(newData);
  }

  return await prisma.expense.update({...});
}
```

### 2.4 Chart of Accounts Rules
- Account number ranges:
  - **1000-1999**: Assets
  - **2000-2999**: Liabilities
  - **3000-3999**: Equity
  - **4000-4999**: Revenue
  - **5000-5999**: Expenses
- Validate account type matches account number range
- Never delete accounts with:
  - Existing journal entry lines
  - Child accounts in hierarchy

### 2.5 VAT Handling
- Default VAT rate: 15%
- VAT Input Account: 2100 (asset - VAT paid on purchases)
- VAT Output Account: (liability - VAT collected on sales)
- Always calculate VAT on taxable transactions
- Include VAT as separate journal entry line

### 2.6 Journal Entry Status Flow
```
PENDING → POSTED → VOID (with reversal)
```
- **PENDING**: Draft, can be modified
- **POSTED**: Finalized, affects GL, requires reversal to change
- **VOID**: Cancelled with automatic reversal entry

### 2.7 Control Account Reconciliation
- **Always** verify control accounts match sub-ledgers:
  - Bank Account (1100) = Sum of posted cashbook entries
  - Accounts Receivable (1300) = Sum of unpaid customer invoices
  - Accounts Payable (2000) = Sum of unpaid vendor invoices

### 2.8 Financial Statement Exclusions
- Exclude from reports:
  - VOID journal entries
  - Reversal entries (VR-/REV- prefix)
  - Entries linked to voided cashbook transactions
  - Entries with null currency

## 3. DATA INTEGRITY RULES

### 3.1 Email Uniqueness (Applications)
- One application per email address
- Validate before creating new application
- Return clear error if duplicate

### 3.2 Soft Deletes
- **Never** hard delete records with:
  - Financial impact (expenses, invoices, journal entries)
  - Audit trail requirements
- Use soft delete flags or reversal entries
- Maintain data for reporting/audit

### 3.3 Audit Trails
- Log all critical operations via `AuditService`
- Include: action, entityType, entityId, performedById, timestamp
- Required for:
  - Journal entry posting/voiding
  - Stage transitions
  - Approval actions
  - Financial transactions

### 3.4 Validation Before Creation
- **Always** validate before creating records:
  - Fund capacity (requestedAmount ≤ fund.remainingAmount)
  - Required documents uploaded
  - Related records exist (foreign keys)
  - Business rules satisfied

## 4. INTEGRATION PATTERNS

### 4.1 Expense → Accounting Integration
```typescript
// When creating expense:
1. Create expense record (status="DRAFT")
2. Call JournalEntryService.createExpenseJournalEntry()
3. Link via expense.journalEntryId
4. Update expense.status = "POSTED"
```

### 4.2 Invoice → Accounting Integration
```typescript
// Invoice creation:
Dr  Accounts Receivable (1300)
    Cr  Revenue Account
    Cr  VAT Output

// Payment:
Dr  Cash/Bank
    Cr  Accounts Receivable (1300)

// Update invoice:
paidAmount += payment
outstandingAmount -= payment
```

### 4.3 Cashbook → GL Integration
- Two-stage: PENDING → POSTED
- PENDING: Captured but not in GL
- POSTED: Journal entry created, affects GL balances
- **Always** create journal entry when posting

### 4.4 Fund Disbursement → Accounting
```typescript
// When disbursed:
1. Create CashbookEntry
2. Auto-create journal entry via cashbook posting
3. Update fund.remainingAmount
4. Link via cashbookEntryId
```

## 5. CODE STANDARDS

### 5.1 TypeScript Standards
- Use TypeScript for all new code
- Define interfaces for complex objects
- Use strict null checks
- Avoid `any` type - use proper typing

### 5.2 Naming Conventions
- **Services**: PascalCase + "Service" suffix (e.g., `ExpenseService`)
- **Controllers**: PascalCase + "Controller" suffix
- **Routes**: camelCase + "Routes" suffix (e.g., `expenseRoutes`)
- **Database fields**: camelCase (e.g., `journalEntryId`)
- **Enums**: SCREAMING_SNAKE_CASE (e.g., `UNDER_DUE_DILIGENCE`)

### 5.3 Error Handling
- Use try-catch blocks in all async functions
- Return descriptive error messages
- Log errors for debugging
- Use appropriate HTTP status codes via ResponseHelper

```typescript
try {
  const result = await Service.operation();
  return ResponseHelper.success(res, result);
} catch (error) {
  console.error("Error in operation:", error);
  return ResponseHelper.serverError(res, error.message);
}
```

### 5.4 Async/Await Pattern
- Use async/await (not callbacks or .then())
- Always await database operations
- Use Promise.all() for parallel operations when possible

### 5.5 Decimal Precision
- Use `Decimal` from Prisma for all monetary values
- NO ROUNDING during calculations (explicitly stated in codebase)
- Only round for display purposes
- Store full precision in database (`@db.Decimal(15, 2)` or similar)

## 6. SECURITY & AUTHENTICATION

### 6.1 Authentication Middleware
- Use `authenticate` middleware for protected routes
- JWT-based authentication
- Validate token on every protected request

### 6.2 Authorization
- Role-based access control (RBAC)
- Check user roles/permissions before operations
- Board members: department="Investments" AND roleCode in ['BOARD_CHAIR', 'BOARD_MEMBER']
- Validate user has permission for action

### 6.3 Data Validation
- Validate all user input
- Sanitize data before database operations
- Check foreign key references exist
- Validate business rules before processing

## 7. EMAIL NOTIFICATIONS

### 7.1 Non-Blocking Email Sending
- Email errors should NOT break operations
- Use try-catch around email sending
- Log email failures but continue processing
- Store notifications in ApplicationNotification table

```typescript
try {
  await EmailNotificationService.send(...);
} catch (error) {
  console.error("Email notification failed:", error);
  // Continue processing - don't throw
}
```

### 7.2 Notification Events
Send emails on:
- Application stage changes
- Task assignments
- Board review requests
- Approval/rejection decisions
- Payment confirmations

## 9. COMMON PITFALLS TO AVOID

### ❌ NEVER DO:
1. **Update posted transactions directly** → Use reversal workflow
2. **Use float/number for money** → Use Decimal type
3. **Create journal entry without balance validation** → Always validate first
4. **Allow invalid stage transitions** → Check validTransitions map
5. **Hard delete financial records** → Use soft delete or reversal
6. **Put business logic in controllers** → Use service layer
7. **Skip audit trails** → Always log critical operations
8. **Round monetary calculations** → Maintain full precision
9. **Create source document without journal entry** → Auto-generate linked entry
10. **Skip email notification errors as fatal** → Log and continue

### ✅ ALWAYS DO:
1. **Use service layer pattern** → Controllers delegate to services
2. **Validate debits = credits** → Before creating journal entries
3. **Use Decimal type for money** → Maintain precision
4. **Create audit trails** → Log all critical operations
5. **Use database transactions** → For multi-step operations
6. **Follow state machines** → Enforce valid transitions
7. **Link journal entries** → To source documents via foreign keys
8. **Check control account reconciliation** → Verify GL matches sub-ledgers
9. **Use try-catch error handling** → In all async functions
10. **Test accounting impact** → Verify financial statements after changes

## 13. DATABASE SCHEMA MANAGEMENT (CRITICAL)

### 13.1 Prisma Schema Modifications
- **NEVER** run `prisma migrate dev`, `prisma migrate deploy`, or rely on Prisma migration history for this project
- **NEVER** use `prisma db push` as the standard way to update production or shared databases (risk of unrelated drift and destructive prompts)
- **ALWAYS** apply DDL using **executable scripts** in `scripts/` that talk to MySQL **directly** (e.g. `PrismaClient` + `$executeRawUnsafe` / `$queryRawUnsafe`, same pattern as `scripts/run-invoice-lifecycle-rate-snapshot-migration.ts`)
- Scripts must be **idempotent** when practical: query `information_schema.COLUMNS` before `ALTER TABLE`, and **verify** columns exist after applying
- After `schema.prisma` changes: run **`npx prisma generate`** only (not migrate/push for team workflow)

### 13.2 Schema Change Workflow
When modifying `prisma/schema.prisma`:

1. **Update Prisma Schema**
   - Make changes to `prisma/schema.prisma`
   - Document the changes clearly

2. **Create a TypeScript migration script** in `scripts/`
   - Name like `run-<feature>-migration.ts`
   - Use `import 'dotenv/config'` and `PrismaClient` with raw SQL
   - Add `npm run db:migrate:<name>` in `package.json` pointing at that script

3. **Run the script** against the target database
   ```bash
   npm run db:migrate:invoice-payment-snapshots
   # or: npx ts-node scripts/run-invoice-payment-snapshot-migration.ts
   ```

4. **Update Prisma Client** (after schema.prisma matches DB)
   ```bash
   npx prisma generate
   ```

5. **Test Changes**
   - Script output should show verify OK for new columns
   - Test affected endpoints
   - Check data integrity

*(Optional: keep a `.sql` copy for audit only — the **canonical** apply path is the TS script, not ad-hoc `mysql` CLI unless ops requires it.)*

### 13.3 Why Manual Migrations?
- Production database requires precise control
- Allows review before execution
- Enables data migration logic within SQL script
- Prevents accidental destructive operations
- Maintains explicit audit trail of database changes

### 13.4 Migration Script Template
```sql
-- Migration: Add category field to Task
-- Date: 2025-11-21
-- Author: [Your name]
-- Description: Adds category column to support task categorization

-- Check if column exists before adding
ALTER TABLE Task
ADD COLUMN IF NOT EXISTS category VARCHAR(255);

-- Add index if needed
CREATE INDEX IF NOT EXISTS idx_task_category ON Task(category);

-- Data migration (if needed)
UPDATE Task SET category = 'General' WHERE category IS NULL;

-- Add constraints (if needed)
-- ALTER TABLE Task MODIFY category VARCHAR(255) NOT NULL;
```

### 13.5 Schema Sync Validation
After manual migration:
```bash
# Validate schema matches database
npx prisma db pull --force  # This will show differences
npx prisma validate         # Verify schema is valid
```

### 13.6 Rollback Strategy
- Always create rollback SQL scripts
- Name format: `YYYY-MM-DD-description-rollback.sql`
- Test rollback script before applying migration
- Keep both migration and rollback scripts in version control
